What is a Database Transaction?

Concurrent Payments: Pay(50) & Pay(30)

If two transactions read Balance = 200 concurrently without concurrency control, both read 200. T1 computes 150 and writes. T2 computes 170 and overwrites T1! The $50 payment vanishes.

T1: Pay(50) Reads 200 → Writes 150
T2: Pay(30) Reads 200 → Writes 170
Final DB State: $170 ($50 deducted payment lost!)
Solution: Enforcing ACID guarantees, locking protocols, or MVCC snapshots.

Real Database Code: MySQL vs PostgreSQL

START TRANSACTION;

-- 1. Read balance
SET @source_balance = (SELECT balance FROM accounts WHERE account_id = 1);
SET @transfer_amount = 100.00;

-- 2. Validate funds
IF @source_balance < @transfer_amount THEN
    ROLLBACK;  -- Abort and rollback
ELSE
    -- 3. Atomic transfer updates
    UPDATE accounts SET balance = balance - @transfer_amount WHERE account_id = 1;
    UPDATE accounts SET balance = balance + @transfer_amount WHERE account_id = 2;
    COMMIT;    -- Persist permanently
END IF;
DO $$
DECLARE
    source_balance DECIMAL(10, 2);
    transfer_amount DECIMAL(10, 2) := 100.00;
BEGIN
    SELECT balance INTO source_balance FROM accounts WHERE account_id = 1;

    IF source_balance < transfer_amount THEN
        RAISE EXCEPTION 'Insufficient funds';
    ELSE
        UPDATE accounts SET balance = balance - transfer_amount WHERE account_id = 1;
        UPDATE accounts SET balance = balance + transfer_amount WHERE account_id = 2;
        COMMIT;
    END IF;
END $$;

Consistency: Invariants & Schema Constraints

Database state transitions only from one valid state to another valid state, upholding all defined rules.

1. Financial Invariants

Total system money Sum(A + B) = $700 remains constant before and after.

2. Check Constraints

CHECK (balance >= 0) prevents overdrafts; violations abort.

3. Foreign Keys

Cannot transfer to non-existent accounts; schema aborts invalid references.

Isolation: Solitary Execution Illusion

Each transaction behaves as if it is the only transaction executing in the universe.

Prevents Lost Update, Dirty Read, Non-repeatable Read, and Phantom Read. Explore Concurrency Timeline ❯

Module 04 • The Shield

SQL Isolation Levels Ladder

Balancing concurrency throughput with anomaly protection.

Level 1 Best Throughput

Read Uncommitted

Allows reading uncommitted dirty changes. Zero isolation.

Level 2 Default in PostgreSQL

Read Committed

Reads only committed data at statement time. Solves Dirty Read.

Level 3 Default in MySQL InnoDB

Repeatable Read

Snapshot taken at transaction start. Solves Non-Repeatable Read.

Level 4 Worst Throughput

Serializable

Strict serial execution illusion. Solves all anomalies including Phantom Read.

Selected Level: Repeatable Read

Prevents Dirty Read and Non-Repeatable Read via Snapshot Isolation.

Architectural Trade-Offs: Locking vs MVCC

Scenario Pessimistic Locking Optimistic MVCC
T1 writes, T2 reads ⏳ T2 blocked until T1 commits 🚀 T2 reads older committed snapshot instantly!
T1 reads, T2 writes ⏳ T2 blocked by shared read lock 🚀 T2 creates new version without touching T1!
Deadlock frequency Frequent across read/write lock orders Extremely rare (reads never acquire locks)
Storage & Cleanup Minimal RAM lock tables Requires Undo logs / Vacuuming dead tuples
Module 07 • Engines Comparison

Engine Showdown: MySQL vs PostgreSQL

Storage architecture, lock granularity, and Write-Ahead Log flushing.

MYSQL ARCHITECTURE 🐬

MySQL (InnoDB vs MyISAM)

InnoDB (Default & Modern) ACID Compliant ✓

Row-level locking, MVCC via Undo Logs in tablespace, next-key gap locks to prevent phantoms.

MyISAM (Legacy) No Transactions ✗

Table-level locks only. Any write closes the whole table to everyone. No crash recovery.

POSTGRESQL ARCHITECTURE 🐘

PostgreSQL (Heap MVCC & SSI)

Tuple Versioning (xmin / xmax) "Reads Never Block Writes" ✓

Stores versions directly in table heap with transaction visibility timestamps; auto-vacuum collects dead tuples.

Serializable Snapshot Isolation (SSI) True Serializable

Tracks dependency graphs (siREAD locks) without blocking reads, aborting only colliding serializable writes.
