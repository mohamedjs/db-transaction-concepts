What is a Database Transaction?

Concurrent Payments: Pay(50) & Pay(30)

If two transactions read Balance = 200 concurrently without concurrency control, both read 200. T1 computes 150 and writes. T2 computes 170 and overwrites T1! The $50 payment vanishes.

T1: Pay(50) Reads 200 → Writes 150
T2: Pay(30) Reads 200 → Writes 170
Final DB State: $170 ($50 deducted payment lost!)
Solution: Enforcing ACID guarantees, locking protocols, or MVCC snapshots.

Real Database Code: MySQL vs PostgreSQL

START TRANSACTION;

-- 1. Read balance
SET @source_balance = (SELECT balance FROM accounts WHERE account_id = 1);
SET @transfer_amount = 100.00;

-- 2. Validate funds
IF @source_balance < @transfer_amount THEN
    ROLLBACK;  -- Abort and rollback
ELSE
    -- 3. Atomic transfer updates
    UPDATE accounts SET balance = balance - @transfer_amount WHERE account_id = 1;
    UPDATE accounts SET balance = balance + @transfer_amount WHERE account_id = 2;
    COMMIT;    -- Persist permanently
END IF;
DO $$
DECLARE
    source_balance DECIMAL(10, 2);
    transfer_amount DECIMAL(10, 2) := 100.00;
BEGIN
    SELECT balance INTO source_balance FROM accounts WHERE account_id = 1;

    IF source_balance < transfer_amount THEN
        RAISE EXCEPTION 'Insufficient funds';
    ELSE
        UPDATE accounts SET balance = balance - transfer_amount WHERE account_id = 1;
        UPDATE accounts SET balance = balance + transfer_amount WHERE account_id = 2;
        COMMIT;
    END IF;
END $$;

Consistency: Invariants & Schema Constraints

Database state transitions only from one valid state to another valid state, upholding all defined rules.

1. Financial Invariants

Total system money Sum(A + B) = $700 remains constant before and after.

2. Check Constraints

CHECK (balance >= 0) prevents overdrafts; violations abort.

3. Foreign Keys

Cannot transfer to non-existent accounts; schema aborts invalid references.

Balancing concurrency throughput with anomaly protection.

How Data Consistency is Preserved in this Mode

ACID guarantees, anomaly prevention mechanisms, and architectural trade-offs.

⚖️ Consistency Mechanism

Row-level locking uses Strict Two-Phase Locking (2PL). Conflicting transactions queue up, ensuring strict conflict serializability.

🚫 Anomalies Prevented

Prevents Dirty Reads (G1) and Lost Updates (P4). T2 cannot observe T1's modified balance until T1 issues a durable COMMIT.

⚡ Throughput vs Trade-Off

Disjoint rows run in parallel with 0 delay. Only transactions contending for the exact same row experience lock-wait latency.

Module 06 • Architectural Reference

Lock Compatibility & MVCC Trade-Offs

Engineering reference matrices for lock compatibility, granularity conflicts, and pessimistic vs optimistic trade-offs.

LOCK COMPATIBILITY MATRIX S vs X

Shared (S) vs Exclusive (X) Locks

Lock Held by T1 \ Requested by T2 Shared (S - Read) Exclusive (X - Write)
Shared (S) ✅ GRANTED (Readers Coexist) ⏳ BLOCKED (Write Waits)
Exclusive (X) ⏳ BLOCKED (Read Waits) ⏳ BLOCKED (Write Waits)

Golden Rule: Multiple readers can share (S+S), but any writer (X) demands exclusive isolation from all readers and writers.

GRANULARITY INTERACTION MATRIX Row vs Table

Multi-Granularity & Intent Locks

T1 Lock T2 Lock Request Outcome & Reason
Row 1 (X) Row 2 (X) ✅ GRANTED (Disjoint rows execute concurrently)
Row 1 (X) Row 1 (X) ⏳ BLOCKED (Same row conflict)
Row 1 (X) Table (X) ⏳ BLOCKED (Intent Exclusive Lock conflict)

Databases use Intent Locks (IX/IS) at the table level so the engine knows a row is locked without scanning millions of rows.

Deep Architectural Comparison: Pessimistic Locking vs MVCC

PostgreSQL • MySQL InnoDB
Scenario / Metric Pessimistic Locking (2PL) Optimistic MVCC (Snapshot Isolation)
T1 writes, T2 reads ⏳ T2 blocked until T1 commits 🚀 T2 reads older committed snapshot instantly (0ms)!
T1 reads, T2 writes ⏳ T2 blocked by shared read lock 🚀 T2 writes new version without touching T1 readers!
T1 writes, T2 writes (same row) ⏳ T2 waits for Row X-Lock ⏳ T2 waits for Row X-Lock (First Committer Wins)
Deadlock frequency Frequent across complex read/write sequences Extremely rare (reads never acquire locks)
Storage & Cleanup overhead Minimal memory (in-RAM Lock Manager table) Requires Undo Log segments or VACUUM daemon for dead tuples

Module 07 • Engines Comparison

Engine Showdown: MySQL vs PostgreSQL

Storage architecture, lock granularity, and Write-Ahead Log flushing.

MYSQL ARCHITECTURE 🐬

MySQL (InnoDB vs MyISAM)

InnoDB (Default & Modern) ACID Compliant ✓

Row-level locking, MVCC via Undo Logs in tablespace, next-key gap locks to prevent phantoms.

MyISAM (Legacy) No Transactions ✗

Table-level locks only. Any write closes the whole table to everyone. No crash recovery.

POSTGRESQL ARCHITECTURE 🐘

PostgreSQL (Heap MVCC & SSI)

Tuple Versioning (xmin / xmax) "Reads Never Block Writes" ✓

Stores versions directly in table heap with transaction visibility timestamps; auto-vacuum collects dead tuples.

Serializable Snapshot Isolation (SSI) True Serializable

Tracks dependency graphs (siREAD locks) without blocking reads, aborting only colliding serializable writes.
