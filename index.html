ما هي المعاملة في قواعد البيانات؟ (Transaction)

سلسلة من عمليات القراءة (Read) والكتابة (Write) على بيانات الـ DB يتم تنفيذها كوحدة واحدة.

Pay(amount) مثال Slide 2 من الـ PDF

1 Read (balance)
200
2 Check (balance >= amount)
200 >= 50 ✓
3 balance = balance - amount
150
4 Pay amount to vendor
إرسال 50$
5 Write (balance)
حفظ 150$
الرصيد النهائي: $200
⚠️ المشكلة الكبرى (Slide 6)

ماذا لو حدثت عمليتان في نفس اللحظة؟

لو قام عميلان بالدفع في نفس اللحظة (Pay 50 و Pay 30) من رصيد 200: كل منهما سيقرأ 200! الأول يحسب الرصيد 150 والآخر يحسبه 170. النتيجة: رصيد خاطئ وضياع إحدى العمليتين تماماً!

T1: Pay(50) Reads 200 → Writes 150
T2: Pay(30) Reads 200 → Writes 170
Actual DB State: 170$ (50$ payment vanished!)

كود التحويل البنكي بلغة SQL: مقارنة MySQL مع PostgreSQL

START TRANSACTION;

-- 1. Read source account balance
SET @source_balance = (SELECT balance FROM accounts WHERE account_id = 1);
SET @transfer_amount = 100.00;

-- 2. Validate balance
IF @source_balance < @transfer_amount THEN
    ROLLBACK;  -- Abort and undo all operations
ELSE
    -- 3. Deduct from source and credit target
    UPDATE accounts SET balance = balance - @transfer_amount WHERE account_id = 1;
    UPDATE accounts SET balance = balance + @transfer_amount WHERE account_id = 2;
    COMMIT;    -- Permanently save changes to disk
END IF;
DO $$
DECLARE
    source_balance DECIMAL(10, 2);
    transfer_amount DECIMAL(10, 2) := 100.00;
BEGIN
    -- 1. Read source account balance
    SELECT balance INTO source_balance 
    FROM accounts 
    WHERE account_id = 1;

    -- 2. Validate funds
    IF source_balance < transfer_amount THEN
        RAISE EXCEPTION 'Insufficient funds';
    ELSE
        -- 3. Execute updates atomically
        UPDATE accounts SET balance = balance - transfer_amount WHERE account_id = 1;
        UPDATE accounts SET balance = balance + transfer_amount WHERE account_id = 2;
        COMMIT;
    END IF;
END $$;

INVARIANTS & CONSTRAINTS

الاتساق (Consistency): الحفاظ على القواعد والثوابت

يجب أن تنتقل قاعدة البيانات من حالة صالحة إلى حالة أخرى صالحة فقط. يجب ألا تنتهك المعاملة قيود الجدول (Constraints) أو القواعد المنطقية للنظام.

1. الثوابت المالية (Invariants)

مجموع أموال النظام Sum(A + B) = 700 يجب أن يظل ثابتاً تماماً قبل المعاملة وبعد انتهائها.

2. قيود الأعمدة (Check Constraints)

منع تحول الرصيد إلى قيمة سالبة CHECK (balance >= 0). أي محاولة تؤدي لسالب تلغي المعاملة فوراً.

3. العلاقات (Foreign Keys)

لا يمكن التحويل إلى account_id غير موجود في جدول الحسابات، وإلا سترفض الـ DB المعاملة وتعمل Rollback.

CONCURRENT INDEPENDENCE

العزل (Isolation): استقلالية المعاملات المتزامنة

حتى وإن تم تنفيذ آلاف المعاملات في نفس الجزء من الثانية، يجب أن تشعر كل معاملة وكأنها الوحيدة التي تعمل على النظام. هذا يمنع التداخل وحالات السباق (Race Conditions).

تعرف على مستويات العزل الأربعة والـ Concurrency Problems

تعرف على كيف يقوم كل مستوى بمنع الـ Dirty Read والـ Non-repeatable Read والـ Phantom Read.

SURVIVING DISASTERS & WAL

المتانة (Durability): آلية سجل الكتابة المسبقة (WAL)

بمجرد إتمام الـ COMMIT، تصبح البيانات مسجلة بشكل دائم ومضمون ضد الضياع، حتى لو انقطعت الكهرباء عن السيرفر في اللحظة التالية مباشرة.

كيف تحقق قواعد البيانات المتانة؟ (Write-Ahead Logging)
1. ذاكرة الرام (Buffer Pool)
Data Pages
تتطاير مع انقطاع الكهرباء
2. سجل WAL (Disk Log)
Append-Only Log
يُكتب على القرص فوراً قبل Commit!
3. ملفات الداتابيز (Data Files)
Table Data on Disk
تُفرّغ لاحقاً عبر الـ Checkpoint
اضغط على "محاكاة انقطاع الكهرباء" لرؤية كيف يسترجع السيرفر البيانات من سجل الـ WAL.

الوحدة الرابعة • درع الحماية

سلم مستويات العزل الأربعة (Slide 17)

كلما صعدت في مستوى العزل، تخلصت من مشاكل التزامن أكثر، ولكن بمقابل انخفاض طفيف في سرعة التنفيذ (Throughput).

Level 1 أعلى أداء (Best Throughput)

Read Uncommitted

لا يوجد عزل تقريباً. أي معاملة يمكنها قراءة تعديلات المعاملات الأخرى حتى قبل عمل Commit.

Level 2 الافتراضي في PostgreSQL

Read Committed

المعاملة تقرأ البيانات التي تم عمل Commit لها فقط لحظة تنفيذ الأمر. يمنع الـ Dirty Read تماماً.

Level 3 الافتراضي في MySQL InnoDB

Repeatable Read

تأخذ المعاملة لقطة (Snapshot) عند بدايتها، وكل قراءاتها تعود لنفس اللقطة. يمنع الـ Non-Repeatable Read.

Level 4 أعلى عزل (Worst Throughput)

Serializable

ينفذ المعاملات وكأنها تعمل بشكل تسلسلي واحد تلو الآخر. حماية تامة من كافة المشاكل بما فيها Phantom Read.

المستوى المختار: Repeatable Read

يحمي من القراءة القذرة والقراءة غير المتكررة عبر تقنية الـ Snapshot Isolation.

الوحدة الخامسة • التحكم المتشائم

أنواع الأقفال (Shared vs Exclusive) ومستوياتها

المنهج المتشائم يمنع حدوث الأخطاء مسبقاً عبر حجز المورد وقفله قبل إجراء التعديلات عليه.

SHARED LOCK (S-LOCK) 📖

قفل القراءة المشترك (Shared Lock)

يسمح لأكثر من معاملة بقراءة نفس الصف في نفس اللحظة (SELECT ... FOR SHARE). ولكن لا يسمح لأي معاملة بكتابة أو تعديل الصف طالما القفل قائم.

Row 42 [Locked with S-Lock]
T1 Read ➔ [Allowed] ✓
T2 Read ➔ [Allowed] ✓
T3 Write ➔ [BLOCKED / QUEUED ⏳] ❌
EXCLUSIVE LOCK (X-LOCK) 🔒

القفل الحصري (Exclusive Lock)

يمنح لمعاملة واحدة فقط تقوم بالكتابة أو الحذف (SELECT ... FOR UPDATE). يُمنع على كافة المعاملات الأخرى القراءة أو الكتابة حتى يتم الـ Commit!

Row 42 [Locked exclusively by T1]
T1 Hold X-Lock (Writing) 🔒
T2 Read ⛔ Blocked
T3 Write ⛔ Blocked

مستويات حصر القفل (Lock Granularity)

Row-Level Lock (قفل على مستوى الصف)

قفل الصف المحدد فقط. يسمح لأي معاملة أخرى بالعمل بحرية على باقي صفوف الجدول دون أي تعطيل. الافتراضي في InnoDB و PostgreSQL.

Table-Level Lock (قفل على مستوى الجدول)

قفل الجدول بأكمله بالكامل. يمنع أي عملية على أي صف آخر! بطيء جداً وكان هو الأسلوب المستخدم قديماً في محرك MyISAM.

Key-Range / Gap Lock (قفل النطاق)

يقفل فجوة أو مدى من الفهارس (مثل الفهارس بين 10 و 20). هذا القفل هو المفتاح السحري لمنع الـ Phantom Read في مستوى Serializable.

التحكم المتفائل: تقنية تعدد النسخ (MVCC)

القراءة لا تعطل الكتابة، والكتابة لا تعطل القراءة إطلاقاً، بفضل الاحتفاظ بنسخ تاريخية متعددة من كل صف!

SNAPSHOT ISOLATION & ROLLBACK POINTERS

كيف تعمل تقنية MVCC في محركات الـ Database؟

عندما تقوم معاملة بتعديل صف، لا تمحو البيانات القديمة، بل تنشئ نسخة جديدة من الصف وتضع مؤشراً للنسخة القديمة. كل معاملة تقرأ النسخة التي كانت موجودة وقت بدء تلك المعاملة!

سلسلة نسخ الصف (Row Version Chain for User: Mohamed)
Version 1 TxID: 100
Balance = $500
Created at: 09:00:00
➔
Version 2 (Latest) TxID: 105
Balance = $400
Pointer to V1 in Undo Log
✨ السحر في ذلك: إذا كانت معاملة سابقة بدأت عند TxID 102، ستقرأ بهدوء Version 1 ($500) دون أن تنتظر المعاملة 105 ودون أن تتأثر بها!

المقارنة العملية: MySQL (InnoDB vs MyISAM) ضد PostgreSQL

الفروق الجوهرية في هندسة التخزين، وتطبيق MVCC، ومستوى الأقفال، ومزامنة سجل الـ WAL.

MYSQL ARCHITECTURE 🐬

MySQL (InnoDB vs MyISAM)

InnoDB Engine (الحديث والافتراضي) ACID Compliant ✓

يدعم الـ Transactions والـ Row-level Locks، ويطبق MVCC عبر سجل التراجع Undo Logs في ملفات Tablespace.

MyISAM Engine (القديم والمندثر) No Transactions ✗

لا يدعم الـ Transactions إطلاقاً! الأقفال فيه على مستوى الجدول بالكامل (Table-level Lock)، ولا يمتلك آلية التعافي من الانهيار (Crash Recovery).

POSTGRESQL ARCHITECTURE 🐘

PostgreSQL (Advanced MVCC)

Heap Multi-Versioning (xmin / xmax) "Reads Never Block Writes" ✓

يخزن نسخ الصفوف مباشرة داخل الـ Table Heap مع وسم xmin و xmax لكل نسخة، ويقوم بعملية الـ Vacuuming التلقائي لحذف النسخ الميتة القديمة.

Serializable Snapshot Isolation (SSI) True Serializability

يقدم أعلى درجات العزل دون الحاجة إلى أقفال ثقيلة، عبر تتبع تعارضات الرسوم البيانية (Dependency Graph Checking) وإلغاء المعاملات المتضاربة فقط.
